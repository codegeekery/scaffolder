# scaffolder-go

**scaffolder-go** is a command-line tool written in Go that lets you create new projects from templates of already-configured frameworks and tools, without needing to remember commands, flags, or manual installation steps.

The core idea is simple: instead of maintaining dozens of hand-made templates that get outdated over time, each framework is added to this repository by running **the framework's own official creation command** (the same one recommended by its maintainers). scaffolder-go takes care of copying that structure into the user's project and installing dependencies automatically.

## ✨ Features

- 📦 Project scaffolding for multiple frameworks/languages/tools from a single CLI.
- 🧱 Each template lives in its own folder inside `structure/`, generated with the framework's official command — these aren't hand-made templates.
- ⚙️ Automatic dependency installation when creating the project (via `setup.go`).
- 🧹 Automatic cleanup: the internal files used during setup don't stay in the user's final project.
- 🤝 Built to grow with community contributions: adding a new framework doesn't require changing the CLI's code.

## 🚀 Installation

### Option 1: Download the binary (recommended)

Download the pre-compiled binary for your operating system from the [Releases](https://github.com/<your-username>/scaffolder-go/releases) section. Builds are available for:

- 🪟 Windows
- 🐧 Linux
- 🍎 macOS

Download the file for your platform, unzip it, and add the binary to your `PATH`.

### Option 2: With `go install`

```bash
go install github.com/<your-username>/scaffolder-go@latest
```

### Option 3: Building from source

```bash
git clone https://github.com/<your-username>/scaffolder-go.git
cd scaffolder-go
go build -o scaffolder .
```

## 🧑‍💻 Usage

```bash
scaffolder create <framework> <project-name>
```

Example:

```bash
scaffolder create deno-fresh my-app
```

This will:
1. Look for the matching folder inside `structure/`.
2. Copy its contents into `./my-app`.
3. Run the internal `setup.go` to install the chosen framework's dependencies.
4. Remove the internal scaffolding files (`setup.go`) so the project is left clean, as if it had been created manually with the official command.

## 📁 Repository structure

```
scaffolder-go/
├── structure/
│   ├── <framework-1>/
│   │   ├── setup.go
│   │   └── ... (files generated by the framework's official command)
│   ├── <framework-2>/
│   │   ├── setup.go
│   │   └── ...
│   └── ...
├── main.go
└── README.md
```

Each folder inside `structure/` represents **one supported framework or tool**. The folder name is the identifier used when calling `scaffolder create <name>`.

### How does `setup.go` work?

Each template includes, at the root of its folder, a `setup.go` file responsible for installing the generated project's dependencies, using that framework's own installation command (`npm install`, `deno install`, `cargo build`, `pip install -r requirements.txt`, etc.).

```go
package main

import (
	"fmt"
	"os"
	"os/exec"
)

func main() {
	fmt.Println("Setting up project dependencies...")

	cmd := exec.Command("deno", "install") // <-- replace with the actual install command
	cmd.Stdout = nil
	cmd.Stderr = nil

	if err := cmd.Run(); err != nil {
		fmt.Println("Error: Failed to install dependencies.")
		os.Exit(1)
	}

	// Self-deletes so it leaves no trace in the user's final folder
	_ = os.Remove("setup.go")

	fmt.Println("Setup completed successfully!")
}
```

At the end, `setup.go` deletes itself: the project left for the end user is indistinguishable from one created by manually running the framework's official command.

## ⚙️ CI/CD — Workflows

The repository has two GitHub Actions workflows in `.github/workflows/`, each with a different trigger and fully independent from one another.

### `release.yml` — Build and publish binaries

**Triggered when:** a **tag** starting with `v` is pushed (`on: push: tags: ['v*']`).

**What's the traditional flow to trigger this workflow?**

```bash
# 1. Stage changed files
git add .

# 2. Commit following Conventional Commits
git commit -m "feat: first scaffolder-go release"

# 3. Push the commit to the main branch
git push origin main

# 4. Create the version tag (follows SemVer: vMAJOR.MINOR.PATCH)
git tag v0.1.0

# 5. Push the tag — this push is what triggers release.yml
git push origin v0.1.0
```

Practical rule for choosing the version number, based on Conventional Commits:

| Commit prefix | Type of change | Bump example |
|---|---|---|
| `fix: ...` | bug fix | `v1.0.0` → `v1.0.1` |
| `feat: ...` | new feature | `v1.0.0` → `v1.1.0` |
| `feat!: ...` or commit with `BREAKING CHANGE` | breaking change | `v1.0.0` → `v2.0.0` |

**What the workflow does:**
1. Checks out the repository and sets up Go 1.22.
2. Compiles the binary for 5 OS/architecture combinations:
   - `windows/amd64`
   - `linux/amd64`
   - `linux/arm64`
   - `darwin/amd64` (macOS Intel)
   - `darwin/arm64` (macOS Apple Silicon)
3. Creates a GitHub Release with the same name as the tag and uploads the 5 binaries as assets, using `softprops/action-gh-release`.
4. Automatically generates release notes (`generate_release_notes: true`) from commits and PRs since the previous tag.

**Requirements:** none special — uses the repository's implicit `GITHUB_TOKEN` (hence `permissions: contents: write`).

### `sync-structure.yml` — Sync templates with R2

**Triggered when:** a push is made to the `main` branch **and** the push modifies something inside `structure/**` (`on: push: branches: [main]: paths: ['structure/**']`). A push that only changes the README, the CLI in `main.go`, or any other file outside `structure/` does **not** trigger this workflow.

**Traditional flow to trigger this workflow:**

```bash
# After adding/editing something inside structure/<framework>/
git add structure/nestjs
git commit -m "feat: add NestJS template"
git push origin main
```

That `git push origin main` is enough — no tag needs to be created for this workflow to run.

**What the workflow does:**
1. Installs `rclone` and configures it to talk to Cloudflare R2 using the S3 provider.
2. Packages **each folder** in `structure/<framework>/` as a `.tar.gz` (`structure/nestjs/` → `dist/templates/nestjs/latest.tar.gz`).
3. Generates a `manifest.json` with the update date and the list of all available templates.
4. Syncs the entire `dist/` folder with the R2 bucket (`rclone sync dist/ r2:scaffolder-dist/`).

This is what lets the scaffolder-go CLI download templates on demand instead of having them bundled inside the binary.

**Requirements:** three secrets configured in the repository (Settings → Secrets and variables → Actions):

| Secret | Purpose |
|---|---|
| `R2_ACCESS_KEY_ID` | Access key for the Cloudflare R2 bucket |
| `R2_SECRET_ACCESS_KEY` | Bucket secret key |
| `R2_ENDPOINT` | S3 endpoint of the R2 bucket |

### Summary: what triggers what

| Action | `release.yml` | `sync-structure.yml` |
|---|:---:|:---:|
| Push to `main` without changing `structure/` | ❌ | ❌ |
| Push to `main` changing `structure/**` | ❌ | ✅ |
| Push of a `vX.Y.Z` tag | ✅ | ❌ |
| Commit with changes in `structure/` + push to `main` + tag afterward | ✅ (by the tag) | ✅ (by the commit to main) |

Both workflows are independent and can run in parallel within the same change cycle. For example, when adding a new template and then releasing a version:

```bash
git add structure/nestjs
git commit -m "feat: add NestJS template"
git push origin main          # triggers sync-structure.yml

git tag v0.2.0
git push origin v0.2.0        # triggers release.yml
```

## 🤝 Contributing

Want to add a new framework? See the full guide in [`CONTRIBUTING.md`](./CONTRIBUTING.md). In short:

1. Create a folder at `structure/<framework-name>` (kebab-case).
2. Inside it, run the framework's official creation command (the same one recommended in the official docs to start a project from scratch).
3. Add a `setup.go` at the root of that folder with the actual dependency installation command.
4. Open a Pull Request.
